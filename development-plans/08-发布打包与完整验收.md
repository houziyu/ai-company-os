# 开发计划 08：Compose 发布包、备份恢复与完整验收

## 可直接交给 AI 的任务

请对前七阶段进行发布前整合，交付可以在新环境自部署的 AI Company OS 试用版本。先审查验收缺口，再修复阻止发布的问题；不要用新增功能掩盖已有缺陷。

## 本阶段结果

用户按 README 配置并启动，完成模型配置、公司创建、代码任务、提案修复和产物下载；服务重启或备份恢复后仍可继续。

## 实施范围

1. Compose 生产配置、锁定镜像、健康检查、迁移顺序、重启策略和数据卷整理；开发配置与用户部署配置分开。
2. 源码部署支持 docker compose up -d --build；如提供预构建镜像，给出固定版本部署方案，实际发布镜像需由用户安排。
3. 首次启动向导校验基础设施、密钥引用和执行器；错误应能定位到具体服务。
4. 增加备份与恢复流程，覆盖 PostgreSQL、产物、非敏感配置和所需秘密的独立恢复说明；在新卷上做真实恢复演练。
5. 升级前备份、数据库迁移和兼容性说明；不能承诺所有迁移可自动回滚，明确回退条件。
6. 审查身份校验、对象权限、CSRF、日志脱敏、目录边界、预算并发、执行器隔离和依赖风险；修复高影响问题。
7. 统一中文界面、空状态、错误、加载、长任务进度和移动端基本可用性；不留下假按钮。
8. 提供清晰运行指标：队列长度、活跃执行、预算剩余、失败数、待审批数；指标来源为真实业务记录。
9. 明确开源许可证选择、第三方依赖许可、贡献说明和版本变更记录；许可证方案在发布前由所有者确认。
10. 形成演示脚本、截图、测试报告和已知限制；准备发布内容但不自动推送公网或外部仓库。

## 发布验收场景

A. 全新环境：初始化所有者 → 创建模板公司 → 配置模型 → 创建项目 → 下载经过验证的代码。
B. 治理闭环：真实验证失败 → Finding → Proposal → 分级批准 → 修复 → 新验证证据。
C. 故障恢复：执行中停止 Worker、重启服务 → 正确恢复或明确中断 → 不重复执行未知副作用。
D. 预算防护：并发申请不能超额；模型超时有保守记账；公司暂停停止新调用。
E. 数据恢复：备份 → 新数据库卷/产物目录恢复 → 登录、历史审计、下载与后续任务均正常。
F. 隔离防护：代码无法访问控制平面秘密、任意宿主路径和未授权网络。
G. 真实模型：完成不同目标的实际 API 验收；密钥或预算未提供时列为发布未完成项，不能用演练报告替代。

## 最终交付

README、配置样例、Compose 文件、版本锁定、数据库迁移、备份恢复说明、完整验收报告、演示步骤、已知限制和后续清单。

“可发布”要求 A—G 的适用项通过，并且不存在尚未处理的高影响安全/数据一致性缺陷。此时系统是受约束的研发协作 MVP，支持范围按实际验证结果声明。
