# AI Company OS 分阶段开发总纲

版本：1.1｜2026-10-29｜用途：交给不同 AI 分阶段实施

开工前先读根目录 AGENTS.md 与 docs/START-HERE.md。架构以 docs/architecture.md 为准；UI 必须遵守 docs/design/ 下的规范；各阶段验收同时遵守 docs/quality-gates.md。本总纲不覆盖这些专项文档的细则。

## 如何使用

每次将本文件、对应阶段计划、当前代码仓库一起交给开发 AI；已有 PRD 可作为产品背景。要求它先检查前一阶段的验收结果，再执行本阶段。每阶段验收通过后再进入下一阶段，同一份仓库连续迭代。

本计划采用前面讨论的 FastAPI + Vue 3 + PostgreSQL 技术路线作为实施基线，Docker Compose 是已确定的标准部署方式。现有 PRD 中的“Python 标准库 HTTP 服务、原生前端、SQLite 起步”已不适用，以本计划为准。现有 company_os/core.py、runtime.py 是未经完整验证的早期草稿，不能视为已完成阶段或直接作为正式架构；可以提取业务思路，正式实现按新工程结构建立。保留旧文件，迁移后在说明中标识其状态。

## 产品不可改变的原则

- 开源、自部署，单公司、单所有者先行，多项目。
- 默认五岗位：CEO、产品经理、技术负责人/开发、QA、DevOps。岗位与 Agent 实例分离。
- 公司模板实例化后允许编辑；管理关系不自动授予资源权限。
- bounded 自主协作，Finding → Proposal → Decision → Task → Result → Knowledge。
- delegated 分级决策：领域内负责人、跨部门 CEO、高风险或超范围人类所有者。
- 按需唤醒；等待期间不持续消耗模型费用。
- 模型首选 DeepSeek V4.1 Flash，模型 ID 可配置，提供 OpenAI 兼容协议适配。
- 代码交付必须有真实文件、测试结果和审计证据；模型自述不能替代验证。
- 技能系统先内置核心工具并预留接口，插件方案仍是待确认项。

## 工程基线

前端：Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus。组件库已在开发前基线选定；阶段 01 验证兼容版本并锁定，按 design-tokens.json 统一主题与尺寸。
后端：FastAPI、Pydantic、SQLAlchemy 2、Alembic。
数据：PostgreSQL 为业务状态的唯一事实来源；模型输出原文可以 JSON 保存，但公司、岗位、任务、执行、预算等核心实体需要明确字段、约束和关系。
进程：web、api、worker、postgres；后续增加受限执行器。API 和 Worker 共用业务模块，独立启动。
队列：首版采用 PostgreSQL 持久队列，事务领取、租约、心跳、幂等。后续按实际需求引入其他队列组件。
实时：REST 操作 + SSE 状态通知，支持断线后的事件补读。
部署：Compose 统一入口、内部网络、数据卷、健康检查；迁移使用独立一次性步骤，不能让多个服务争抢执行迁移。
执行：任务代码在独立隔离环境执行；模型不接触控制平面凭据。
认证：单所有者登录、服务端会话；浏览器写操作保护；不做完整多租户。
版本：第一阶段选择相互兼容的稳定版本并锁定；镜像和依赖不能使用无约束 latest。

建议目录：
backend/app/{api,domain,services,models,providers,workers}
backend/alembic
backend/tests
frontend/src/{views,components,api,stores}
executor/
deploy/
docs/

允许在保持模块边界的前提下调整目录，不允许为了“先进”提前拆成微服务。

## 阶段顺序

| 阶段 | 可看到的结果 | 依赖 |
|---|---|---|
| 01 工程与部署基础 | Compose 启动，登录后看到中文空控制台 | 无 |
| 02 公司与模型中心 | 创建公司、五个员工、编辑组织、配置模型 | 01 |
| 03 持久任务与预算 | 任务真正排队、运行、暂停、恢复，预算受控 | 02 |
| 04 隔离执行与工具网关 | 受限代码在隔离环境真实运行，产生测试证据 | 03 |
| 05 五岗位研发闭环 | 输入小型代码目标，交付源码、测试和说明 | 04 |
| 06 提案与分级治理 | 发现问题、审批、升级、修复形成闭环 | 05 |
| 07 长期项目与记忆 | Git 项目、依赖任务、项目记忆和跨天恢复 | 06 |
| 08 自部署发布验收 | 新环境按文档部署并完成完整演示 | 07 |

阶段 01—04 是基础；阶段 05 是首次有实际研发价值的里程碑；阶段 06 是体现 AI 公司治理特色的 MVP；阶段 08 才是可供外部用户试用的发布候选。

## 给所有开发 AI 的统一指令

你正在接力开发 AI Company OS。阅读本总纲、本阶段计划、仓库现状和上一阶段交接记录后，直接实施本阶段，不反复询问已明确的选项。

1. 先报告前置条件是否成立。缺少前置阶段时列出具体缺口，不凭空假定已完成，也不把上一阶段整体重写。
2. 将本阶段拆成小任务；保持可运行；只引入本阶段必要依赖。
3. 服务端强制执行权限、预算、状态迁移和幂等；前端隐藏按钮不能作为安全控制。
4. 真实模式缺少密钥时明确提示；演练/模拟数据必须显式标识，不能静默切换或伪造成功。
5. 不将生成代码放到宿主机或 API/Worker 进程中直接执行。
6. 用户未提供模型密钥时，用协议模拟服务验证适配与失败路径；真实模型验收标记“未执行”，不能以此阻止其他工程工作。
7. 在既有接口上增量演进。破坏性变更需给出迁移方案，不删除用户数据或历史执行。
8. 对事务、并发、权限、状态恢复、执行隔离编写有意义的测试；完成本阶段验收，不以空壳页面或假按钮交付。
9. 文档中区分已实现、已测试、未验证、后续计划；不得宣称全面安全或任意任务都能完成。
10. 不自动发布公网、推送外部仓库、购买服务或执行生产部署。

## 每阶段必须交付

- 可运行的代码、数据库迁移及必要配置样例。
- 对应页面和服务端接口，接口错误可在页面上理解。
- 本阶段验收报告 docs/acceptance/phase-XX.md，列出实际命令、结果、证据、未验证项。
- docs/handoff/phase-XX.md：实现范围、关键设计、接口和表变更、启动方法、已知问题、下一阶段入口。
- 更新 README 和必要架构记录；若对外使用，提供与实际代码一致的说明。

测试失败或验收缺项不能写“全部完成”。交接记录要足够让另一名 AI 在不读取聊天历史的情况下继续工作。
