# ADR-0005：阶段 03 复审修复的锁序、预算证据与游标兼容

日期：2026-11-02  
状态：采用（用户授权修复阶段 03 复审缺陷）  
影响：补充 ADR-0004；不改变阶段范围、技术栈或至少一次事件投递约定。

## 问题

[复审](../acceptance/phase-03-recheck.md)发现 V2-1—V2-5：心跳等待锁后复活租约、步骤与恢复死锁、跨尝试重复扣费、取消未知用量错误释放、旧游标升级漏事件。

## 决定

1. 心跳先取得执行行锁并刷新 ORM 缓存，再读取当前时间，检查 token、RUNNING 和未过期租约。心跳只锁执行，不向上申请公司/任务锁。其他执行写入同样刷新锁定的任务和执行。
2. 步骤开始/结束、完成、恢复、取消、重试统一按公司→任务→执行→预算的顺序取得所需锁；创建任务是公司→项目→新任务→预算。公司使用 PostgreSQL `FOR NO KEY UPDATE`，SQLAlchemy 表达为 `with_for_update(key_share=True)`（没有 `read=True`）。它与业务写锁互斥，但兼容插入外键取得的 `KEY SHARE`。领取保持任务级 `SKIP LOCKED`，不申请公司业务写锁；领取不执行付费调用，付费门禁在开始步骤时执行。公司暂停/恢复也使用相同公司锁。所有这些事务仅做数据库工作，不包围外部调用。
3. 未领取的 QUEUED 重试，其新规划预留没有调用，取消时释放。已领取的尝试只查询本次 execution 的步骤与 CALL 预留。旧步骤、执行、账本和已结算预留不改动。取消状态不证明零用量：已有步骤的未知用量按整笔 CALL 预留保守结算；已知零用量按 0 结算。
4. 保留 `e5b7c9d1a2f4` 原迁移，追加 `f6c8d0e2b4a7` 数据迁移。旧客户端保存原事件 ID，e5 客户端保存 published_seq，两者数值可能重叠且顺序可能不同，无法凭一个整数可靠辨别来源。因此将全部现存通知的 published_seq 移到 `max(max(id), max(published_seq))` 以上，原已发布通知保持发布顺序，未发布通知按 ID 接在后面。使用与发布器相同的 advisory lock 和事件表锁保证迁移一致。

## 兼容性与代价

- 升级后，携带任一合法旧游标的客户端会重新收到历史通知，再接收新通知。这是一次有意的历史重放，保证不漏事件；不能宣称跨升级无重复。页面根据通知重新读取后端状态，不把通知本身用作再次执行业务命令的授权。外部消费者应按稳定事件 ID/业务标识去重，不能把重新发布解释为新增业务操作。
- 只更新事件的投递元数据；事件 ID、内容、时间、业务记录和账本保留。没有新业务表或 API 格式变更。
- 回退新迁移至 e5 不把游标改回小值，因而不丢已有续读位置。再次升级会再次重放。继续降级至 c41 会删除 published_seq，不能保证在线续读兼容；必须停服务、备份并协调客户端重置，不能作为无损在线回退。
- 同公司的短写事务会串行通过公司锁；独立任务领取仍可并行。未进行容量压测，不宣称吞吐量不变。
- 对已被旧缺陷误记的真实账本不自动冲销。旧用量未知，不能通过批量“修复”历史账本猜测真实花费；如已有受影响业务数据，应按执行证据另行核对。

## 验证

正式回归位于 `backend/tests/test_phase03_recheck_fixes.py`，使用真实 PostgreSQL 锁等待、两会话交错、跨尝试预算与历史快照、旧 ID 空洞、混合游标顺序、升级/回退/再升级与 Alembic schema 检查。实际结果见[本轮验收](../acceptance/phase-03-v2-fixes.md)。
