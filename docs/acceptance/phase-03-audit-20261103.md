## 问题与修复建议

### A1 · P1：探测的暂停门禁不在预留事务内重检

位置：`backend/app/services/model_centre_service.py:884–895,1027–1037`；`budget_service.py:366`。

`probe_model()` 在请求会话里无锁读取公司状态，随后另开事务持有预算。虽然 `reserve_company_allowance()` 会取得公司锁，它没有检查 PAUSED。暂停若在初次读取后、预算事务拿锁前提交，探测仍会创建预留并调用供应商。

复现：在生产方法 `_commit_probe_intent` 入口安排另一会话通过 `CompanyGovernanceService.pause()` 提交暂停，再继续原方法。真实 PostgreSQL 状态已为 PAUSED，模拟 HTTP transport 仍收到 **1 次**请求。不是要求撤销已经发出的调用，而是暂停提交时连调用意图/预留尚未建立。

建议：在提交探测意图与预留的同一事务、同一公司锁内重读并校验暂停状态；拒绝时不得提交新的付费预留。测试：`test_pause_committed_before_probe_reservation_blocks_call`。

### A2 · P1：部分探测用量被当作完整用量，释放未知部分额度

位置：`backend/app/services/model_centre_service.py:1089–1095`。

这里用 `prompt_tokens is not None or completion_tokens is not None` 判断完整用量，再把缺失维度按 0 相加。适配器和探测响应使用的是两维均已知语义，因此同一次调用会出现 API 显示未知、预算账本却显示已知的矛盾。

复现：供应商只返回输入 7 Token、不返回输出。响应 `usageKnown=false`，512 Token 预留却只结算 **7**，`needs_reconciliation=false`，其余 505 变回可用。违反阶段 03 未知用量保守处理要求。

建议：完整计量必须要求两维均已知；部分数据保留在用量证据中，但总预算按未知量保守结算并待核对。测试：`test_partial_probe_usage_is_conservative`。

### A3 · P1：缺少密钥的本地拒绝永久占用公司预算

位置：`backend/app/services/model_centre_service.py:1078–1079`（及 909–916 的预先预留）。

无密钥或环境变量缺失由适配器在预留提交后拒绝；`_settle_probe_budget()` 遇到 `call_count==0` 直接返回，注释假定“未创建预留”，与实际顺序不符。

复现：公司存在、供应商没有密钥，点击探测返回 `MISSING_SECRET`、`callCount=0`，公司却留下 **512 Token RESERVED**。重复点击会继续占用，且没有实际调用可供结算，最终阻止合法任务。

建议：调用前验证可用密钥；对确定未发起调用的本地拒绝，仍应幂等释放已经提交的预留。测试：`test_missing_secret_does_not_leave_budget_reserved`。

### A4 · P1：一个执行的有效租约可以修改另一个执行的步骤

位置：`backend/app/services/execution_service.py:416–419,433–440`。

`finish_step()` 校验传入 execution 的租约，却仅按独立 `step_id` 读取步骤，没有校验 `step.execution_id == execution_id`；预留也只按 step_id 取。因此持有 B 的有效租约即可写 A 的步骤和任务预算，A 自己是否已经失租并不参与校验。

复现：创建两个合法任务并分别领取，用第二个 claim 回写第一个步骤。第一个步骤从 **RUNNING 改为 SUCCEEDED**。这是内部 Worker 服务的隔离缺口；本轮没有发现直接对外暴露该写入的 HTTP API，不将其描述成匿名攻击路径。

建议：在同一锁保护下按 execution_id + step_id 定位步骤及其预留，不匹配即拒绝，覆盖跨任务和跨历史尝试场景。测试：`test_fence_cannot_modify_step_of_another_execution`。

### A5 · P1：重复步骤回写覆盖证据，却不更新已结算账本

位置：`backend/app/services/execution_service.py:425–438`。

即使步骤已完成，方法仍覆盖状态、完成时间和用量；但已 SETTLED 的预留不会再次查询到。这会破坏步骤证据与账本的一致性，后续 `complete()` 又从被改写的步骤汇总公司/项目用量。

复现：同一有效执行内，步骤第一次结算 40 Token，再次回写 7 Token，最终 **步骤显示 7、任务层结算仍为 40**。新回写不能因结算唯一索引存在就被视为幂等。

建议：已完成步骤禁止变化；同内容重复交付返回已有结果，冲突内容明确拒绝。测试：`test_duplicate_step_result_keeps_usage_consistent`。

### A6 · P2：重试命令没有持久幂等标识，可额外调度一次执行

位置：`backend/app/api/v1/tasks.py:567–580`、`backend/app/services/task_service.py:657–745`。

接口不接收/保存重试幂等键或目标尝试版本，只检查任务当前状态。首次 retry 已成功但响应丢失时，若其新尝试已经再次失败，用户重发原请求就会被当作又一次授权，建立第三次执行和新规划预留。

复现：永久失败任务→retry→第二次失败→重发同一请求，Worker 又成功领取并执行第三次。测试附带同一 `Idempotency-Key`，当前接口完全忽略；这不是既有 API 声称支持该 header，而是证明目前没有可用的命令去重契约。

建议：为逻辑重试保存幂等键、目标尝试/版本和结果，前端网络重提沿用同一键；新重试另取键。测试：`test_repeated_retry_command_does_not_schedule_another_attempt`。

### A7 · P2：步骤变更没有写入 SSE 进度事件

位置：`backend/app/services/execution_service.py:388–396,445–452`。

`start_step()` 和 `finish_step()` 只写步骤与预算，不写领域事件。前端虽订阅 `TASK_STEP_UPDATED`，后端只有该枚举定义，没有发布路径。

复现：合法开始并完成一个步骤，事务提交后该任务的 `TASK_STEP_UPDATED` 事件仍为 **0 条**。任务开始通知后的状态读取一旦完成，中间步骤将一直不更新，直到结束等其他事件到达；断线补读也无法补出从未持久化的通知。

建议：步骤状态变更与进度事件同事务提交，包含 task/execution/step 标识。测试：`test_step_update_publishes_progress_event`。

### A8 · P2：最终事件后的读取失败被吞掉，旧状态仍显示实时更新

位置：`frontend/src/views/TaskDetailView.vue:73–90`（事件处理另见 144–153）。

事件到达就推进 lastEventId、设置 live，然后调用 `load(true)`；该模式失败时不记录错误、不标旧数据、不安排重试。若收到的是最终事件，之后可能再无本任务通知，页面就长期停在 RUNNING，仍显示“已连接，实时更新中”。

复现：真实 Vue 组件挂载，初始 RUNNING；发送 TASK_SUCCEEDED 事件；随后 GET 抛 NetworkError。页面仍是 **执行中 + 已连接，实时更新中**。这是 jsdom 组件验证，不是真实浏览器断网验收。

建议：将 SSE 连接状态与快照新鲜度分离；读取失败保留旧数据并明确提示，重试直到校准成功，重连时也重新读取。测试见 `ui-audit.spec.ts`。

### A9 · P2：执行详情从全公司最近 200 条账本筛选，旧执行会显示零用量

位置：`frontend/src/views/ExecutionDetailView.vue:54–61,71–79`；后端 `budget_service.py:730–739`。

页面先取全公司最近 200 条，再筛选 executionId 并求和。较早执行会随着其他任务产生账本而被挤出，缺失记录被 reduce 初始值 0 伪装成零用量，也会丢掉待核对提示。

复现：连续运行 26 个正常演练任务。第一个执行接口仍报告 **settledTokens=500**，按照页面实际使用的接口和筛选算法计算却是 **0**。数据库证据没有丢失，错误发生在查询范围和页面投影。

建议：服务端先按 executionId 过滤再分页；汇总基于完整执行账本或执行事实，不对被截断的数据集求总量。测试：`test_execution_page_projection_keeps_old_attempt_usage`。

### A10 · P2：任务看板和独立执行详情不会随 Worker 进度刷新

位置：`frontend/src/views/ProjectsView.vue:107–142`、`frontend/src/views/ExecutionDetailView.vue:50–69`。

两页只在挂载/人工切换项目时加载，没有 SSE、轮询或共享失效订阅；AppShell 也未向其提供任务刷新事件。用户停留在看板或打开正在运行的独立执行页，即使 Worker 已完成，卡片/步骤仍维持旧状态，必须离开重进或手动刷新浏览器。

建议：两页接入事件后的权威读取和断线校准，避免仅任务详情具备实时能力。本项为静态代码确认，未宣称做过真实浏览器端到端复现。
