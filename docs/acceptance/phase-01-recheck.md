## 新发现 R7 · P2：旧请求迟到的 401 清除新登录会话

位置：`frontend/src/api/client.ts:151–154`、`frontend/src/api/auth-failure.ts:11–13`、`frontend/src/stores/session.ts:44–48`。

客户端在收到任一受保护请求的 401 时，无条件广播失效；store 随即清空当前会话。请求和通知不带发起时的会话版本，因此无法判断失败属于旧会话还是已经重新登录的新会话。

复现顺序：

1. 旧会话失效，两个受保护请求在途。
2. 第一个 401 到达，前端正确变为 anonymous，用户可以重新登录。
3. 用户登录成功，store 已变回 authenticated。
4. 第二个旧请求的 401 此时才到达，store 被再次清成 anonymous、用户信息清空。

本轮用真实客户端、真实 store 和受控 fetch 响应顺序复现，断言结果为 **expected authenticated / received anonymous**。没有修改服务端校验，也没有使用固定 sleep。浏览器中跨页面请求未取消、网络延迟等情况允许这种响应顺序；本轮是传输替身的确定性验证，未声称已完成真实网络故障复现。

影响：已成功登录的用户重新看到“请重新登录”，路由守卫按未登录处理；服务器的新会话并没有因此被撤销。这是前端状态一致性与可用性问题，不是越权或密码泄漏。

修复建议：为会话引入递增版本/代次；请求发起时捕获版本，401 只失效同一版本的会话。登录/初始化成功、注销等会话切换需推进版本。统一处理 `refresh()` 自身的错误/成功回写，避免它在版本检查之外覆盖新状态；不要忽略所有 401，也不要只对登录后的短时间屏蔽错误。保留当前真实会话失效和公开登录命令错误的测试。
